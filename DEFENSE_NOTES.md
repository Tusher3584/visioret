# Visioret — Defense Notes

Questions a panel is likely to ask, the honest answer, and **where the
evidence lives** so nothing has to be recalled under pressure.

Rule for every answer below: cite a number that can be regenerated, or say
plainly that something was not done. A defensible "we didn't do that, here's
why" beats a confident claim that doesn't survive a follow-up.

---

## 1. Dataset and methodology

### "How do you know your test set isn't contaminated?"

Two-part answer, and the second part is the one that matters.

Kermany's **official** train/test split leaks roughly **85% of its test
patients into train** — verified, not assumed. So it is not used. All images
are pooled and re-split by patient with `GroupShuffleSplit`, and the split is
persisted to `patient_split.json` so the held-out set never moves.

**Then volunteer the caveat before being asked.** The grouping key is
`f"{class}-{patient_number}"`, and 896 of 4,657 numeric IDs (19.2%) appear
under more than one class — clinically coherent, since a patient can have wet
AMD in one eye and drusen in the other. So one patient can be split into up
to three groups: **5,375 of 13,146 test images (40.9%) come from a patient
seen in training.**

The direction was measured, not guessed:

| Subset | n | Accuracy | Macro F1 | DRUSEN F1 |
|---|---|---|---|---|
| Full test set | 13,146 | 0.9517 | 0.9233 | 0.817 |
| Leaked | 5,375 | 0.9180 | 0.8878 | 0.752 |
| **Clean** | 7,771 | **0.9750** | **0.9541** | 0.882 |

The model scores **worse** on the leaked patients — the opposite of
memorisation — because those are the multi-diagnosis cases sitting on the
CNV/DRUSEN boundary. So 95.17% is *conservative*, and 97.50% is the genuinely
patient-disjoint figure.

**Evidence:** `python -m model.audit_patient_leakage` regenerates that table.
Also `model/dataset.py` (KNOWN LIMITATION docstring), README "Known
limitation: patient grouping", R2 in `REVIEW_CHECKPOINTS.md`.

**If asked why it isn't fixed:** correcting the key changes which patients
land in which split, which invalidates the split the deployed checkpoint was
trained against — it requires a full retrain. It is documented rather than
hidden, and the error is in the conservative direction.

### "Isn't 95% just the model memorising one dataset?"

No, and there is a measured answer. Trained on Kermany alone the model scored
**82.0% / 0.78 macro-F1** on external data, with DRUSEN recall at **0.48**.
After training across four datasets: **88.1% / 0.90**, DRUSEN recall **0.79**,
while in-distribution accuracy barely moved (95.42% → 95.17%).

That external number is on **2,712 images from patients reserved before
training**, across three other hospitals/scanners (Noor Eye Hospital, OCTDL,
Duke). **The external split is unaffected by the grouping caveat above** —
OCTDL keys on the bare numeric ID, Duke on the per-patient volume folder, and
Noor's class prefix is genuinely correct there because its patient folders are
numbered independently inside each class.

**Evidence:** `model/checkpoints/cross_dataset_evaluation_report.txt`,
regenerated by `python -m model.evaluate_cross_dataset`.

### "Why exclude the AMD class from OCTDL and Duke?"

Because neither splits AMD into CNV vs DRUSEN, and mapping it would require a
clinician's relabelling rather than a guess. Excluding data is the honest
choice; inventing labels is not.

### "Your Noor labels come from filenames?"

Yes, deliberately. Noor encodes the label per B-scan (`003_Normal.jpg`), and a
diagnosed patient's volume still contains normal-looking slices. Using the
**folder** label would have injected real label noise into thousands of
images.

## 2. The model

### "Why ResNet-50 and not something newer?"

Transfer learning from ImageNet with `layer3`/`layer4`/`fc` unfrozen
(22.1M of 23.5M parameters trainable). It is a well-understood baseline whose
Grad-CAM behaviour is well characterised — which matters when explainability
is the point of the project, not accuracy alone. Be ready to say that a newer
backbone is a reasonable next step and was not benchmarked.

### "Why is confidence always ~100%?"

Raw softmax output, which is characteristically overconfident. **No
calibration analysis was done** — say so directly. Temperature scaling or
reliability diagrams would be the standard next step. This is listed as a
known gap in `FEATURES.md` §12.

### "Can you prove the Grad-CAM is meaningful?"

10 overlays were reviewed across all four classes, including the known
CNV/DRUSEN confusion cases. The misclassified ones still localised to
sensible tissue — which establishes the confusion is a *classification
boundary* problem, not an explainability failure. Grad-CAM++ was therefore not
pursued, and no quantitative attribution comparison was run.

Also worth mentioning: the overlay is rendered at the scan's **own
dimensions**. An earlier version squashed a 768×496 scan into a 224×224
overlay, so the heatmap no longer aligned with the image beside it — a
presentation bug that would have mislocated findings for a viewer. Found and
fixed in review (R2-3).

### "What stops it diagnosing a photo of a cat?"

A two-stage gate before the classifier ever runs: a grayscale heuristic, then
a **CLIP zero-shot** check against 10 prompts where the OCT prompt must win
the argmax. Rejection returns **HTTP 422 with no diagnosis at all** — verified
in the UI as well as the API.

**Tell the story of why it is CLIP.** The first design measured feature
distance from a centroid calibrated on Kermany images. It rejected **3 of 5**
genuine Noor scans, because "is this an OCT scan?" had quietly become "does
this look like a *Kermany* OCT scan?". CLIP needs no per-dataset calibration.

And the second failure, found during review: a grayscale confusion-matrix
plot was **accepted at p=0.848** and classified DME at 77%. Cause is
structural — argmax over a fixed prompt set can only reject what some prompt
*describes*, and nothing described a chart. Two prompts added; re-validated
**171/171 real OCT images still accepted** across three sources.

**Evidence:** `model/clip_ood.py`, R1-11 and R5 in `REVIEW_CHECKPOINTS.md`.

### "Is the training reproducible?"

The **split** always was — `GroupShuffleSplit(random_state=42)` plus a
persisted JSON. The **run** was not until this review: there was no
`torch.manual_seed`, so head initialisation, shuffle order and augmentation
varied. Now seeded (`SEED = 42`, seeded DataLoader generator, seeded workers).
Be honest that the *deployed checkpoint* predates that fix, so it cannot be
bit-reproduced — only the methodology can.

Both evaluation scripts **do** reproduce their published numbers exactly:
0.951696 / 0.923307 and 0.881268 / 0.895484 on re-run.

## 3. Engineering

### "Why does this need a database / accounts at all?"

Because a reviewer correction writes a human label asserting the model was
wrong — exactly the record that would feed a retraining loop. That needs
provenance and a qualified author. Hence three roles: viewer (own scans),
reviewer (all scans + record corrections + read metrics), admin (accounts).

Two deliberate asymmetries worth stating: **ownership governs visibility,
role governs authority** — a viewer can see their own scan but still cannot
assert the model was wrong on it. And **admin never spreads through the API**:
it is granted only by hand against the database, so administrative privilege
always originates with someone who has database access.

**Live demo if asked:** promote a viewer to reviewer in the admin page, and
that account can read `/api/metrics` immediately; demote, and it is 403 again
— because roles are resolved from the database per request, not frozen into
the token at login.

### "How do you know the permissions actually work?"

The full matrix was probed end to end, every cell:

| Endpoint | anon | viewer | reviewer | admin |
|---|---|---|---|---|
| `GET /api/metrics` | 401 | 403 | 200 | 200 |
| `GET /api/admin/users` | 401 | 403 | **403** | 200 |
| `PUT /api/scans/{id}/feedback` | 401 | 403 | 200 | 200 |

Plus: forged/tampered/`alg=none`/expired JWTs all rejected; SQL injection
parameterised away; stored XSS rendered inert (0 injected tags, verified by
counting them in the DOM); admin cannot grant admin, demote another admin, or
change their own role.

**Evidence:** R5 and R7 in `REVIEW_CHECKPOINTS.md`.

### "What about privacy for people who don't sign in?"

Anonymous scans are scoped by an opaque ID in **`sessionStorage`**, so history
lasts exactly as long as the browser session. A **missing** ID matches
*nothing* rather than every anonymous row — otherwise omitting the header
would re-expose everyone's history.

Proven, not asserted: two anonymous sessions each see only their own scan, a
signed-in viewer supplying someone else's session header gains nothing, and
requesting another session's scan by ID returns 404.

**The one honest exception:** `/media/scans/<uuid>.jpg` is served without
authentication. Filenames are uuid4 so they cannot be guessed, but possession
of the link is the capability and it never expires. This is a deliberate
trade-off (plain `<img>` tags cannot send an Authorization header) documented
in `backend/main.py`, and it is the first thing to close for real patient
data. **Volunteer this rather than being caught by it.**

### "Is it deployment ready?"

As a self-contained research application, **yes** — verified by cloning the
repo fresh and following the README: two commands and one generated secret
reach a working system in ~66 seconds, with all 7 migrations applied
automatically, model weights downloaded, and the published metrics seeded from
a committed file (so the metrics page works on a machine that has never seen
the dataset).

As an internet-facing service, **no**: no TLS, credentials and origins
hardcoded for local use, single-instance assumptions, and a ~686 MB / ~3 GB
footprint that exceeds free hosting tiers. Those are scope boundaries, and
they are written down in R8 rather than implied.

## 4. What went wrong (expect this question)

Have two or three ready. They demonstrate engineering judgement better than
any success does.

1. **Dataset leakage in a published dataset.** Found ~85% of Kermany's
   official test patients also in train. Response: ignore the official split
   and re-split by patient.
2. **A checkpoint-contamination bug.** Smoke tests shared the real checkpoint
   path, so a lucky 32-image score became the "best to beat" and blocked five
   genuinely-trained epochs from ever being saved. Fixed with an isolated
   smoke-test path.
3. **A safety gate that rejected real patients.** The original OOD detector
   turned away 3 of 5 genuine Noor scans because it was calibrated on one
   dataset. Replaced with a calibration-free approach.
4. **A negative result that was kept.** OCT-specific preprocessing (speckle
   denoising, B-scan flattening, retinal cropping) was fully built, wired in,
   and evaluated — and did **not** beat the plain baseline. It was reverted
   rather than shipped, and the code is kept as evidence the idea was tested.
5. **An animation that decided whether content existed.** Seven separate bugs
   where a UI animation gated real information, including page content sitting
   at `opacity: 0` in a background tab. The lesson became a rule enforced in
   code: an animation may decorate a transition, never determine whether
   content is visible.

## 6. Things to be careful about in the live demo

- **Don't register accounts on `.test`, `.local` or `localhost`** — RFC 2606
  reserved domains are correctly rejected with a 422. Use a real-looking
  domain.
- **Ports 5433 / 8000 / 5173 are hardcoded** in `docker-compose.yml`. Check
  they are free on the demo machine beforehand.
- **First boot downloads model weights.** Start the stack before the session,
  not during it — a cold start is ~66s, and it needs network access.
- **The metrics page is reviewer-only.** Have a reviewer account signed in, or
  an examiner will see a "sign in to view" prompt rather than your results.
- **Have a non-OCT image ready.** Rejecting it is one of the most convincing
  things to demonstrate: it shows the system knows what it does not know.
